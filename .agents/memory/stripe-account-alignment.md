---
name: Stripe account alignment
description: Prevents mixing Replit-connected Stripe resources with direct Netlify credentials.
---

The Stripe Price ID, server API key, and webhook signing secret must all come from the same Stripe account and mode. A valid key can still fail to read a Price when it belongs to another account, is live-mode instead of test-mode, or is restricted. The same webhook URL can exist in multiple Stripe accounts and modes; matching URL alone does not establish which one Netlify actually uses.

**Why:** External Netlify billing uses direct server-only Stripe credentials, while Replit development can use the separate Stripe connector. A Price can be valid in the connector account while inaccessible to Netlify. A subscription created before the correct webhook destination exists, or before its endpoint subscribes to invoice.paid, will also remain unknown to the scorecard even though its payment succeeded; later enabling the event is not proof of retroactive delivery.

**How to apply:** Before Checkout verification, compare the Price, API key, and exact deployed endpoint's signing secret inside one account and mode. Stripe can have several snapshot and thin-payload destinations at the *same URL*; check the individual destination's signing secret, payload format, event subscriptions, and per-event HTTP response rather than treating its URL or an invoice in its history as successful delivery. Re-enabling a failing broad destination is not reconciliation. If a live subscription predates the correctly signed destination, replay its authentic event only to the intended endpoint after checking its response, or update that subscription's metadata to trigger reconciliation; a checkout-session event alone only links the customer. For scorecard billing evidence, separately verify an authentic invoice.paid delivery and the restricted report's storage; an old invoice does not arrive merely because the subscription is enabled later. A suppressed count under ten cannot prove one receipt from the report alone.

Stripe's Node SDK can expose a signature-verification exception with `name: "Error"` but `type: "StripeSignatureVerificationError"`. If sanitized production logs record only `name`, a plain `Error` cannot distinguish an invalid destination signing secret from missing configuration. Compare configuration privately, or log the safe error type before diagnosing from a 503; never request the secret value in chat.
