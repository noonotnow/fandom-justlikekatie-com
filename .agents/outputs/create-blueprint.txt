1. Current Architecture Snapshot 
1.1 Single-Operator Baseline 
The existing CREATE application is structured as a single-process Node.js/Express server serving one 
authenticated operator. The data layer uses either SQLite (development) or a single-schema PostgreSQL 
database with no tenant isolation. Social credentials are stored as plaintext environment variables or a 
single row in a config table. Content publishing is either manual (copy-paste) or triggered by a single 
hand-written cron job. Media files are stored on local disk or a single unscoped cloud bucket folder. 
There is no job queue, no retry logic, and no audit trail. 
1.2 Key Limitations 
●​ No row-level isolation: All data is globally readable by any authenticated session; there is no 
concept of tenancy. 
●​ No OAuth token storage per user or team: Credentials are global, cannot be scoped, rotated per 
team, or revoked independently. 

===== PAGE 5 =====
●​ No job queue: Publishing is synchronous or cron-based with no retry, dead-letter handling, or 
status tracking. 
●​ No workspace concept: The data model has no grouping unit between the platform and 
individual content items. 
●​ No role system: Anyone with the single password can perform any action including deletion and 
credential changes. 
●​ No media pipeline: Files are stored without thumbnail generation, format validation, or 
platform-specific resizing. 
●​ No audit trail: Destructive or privileged actions are unlogged. 
●​ Local file handling: Ephemeral Replit filesystem cannot persist large media across deploys.

2. Target Architecture Overview 
2.1 Design Pillars 
●​ Workspace Isolation: Every data record is scoped to a workspace (one workspace = one 
team/brand). RLS enforced at the database layer ensures isolation even if the API layer has a 
bug. 
●​ Stateless API with Stateful Queue: The Express API tier is horizontally scalable and stateless. All 
async work (publishing, media processing, notifications) is delegated to BullMQ workers backed 
by Redis. 
●​ Encrypted Credential Store: Each workspace stores its own OAuth tokens for each connected 
social platform, encrypted at rest with AES-256-GCM. No credentials are ever stored in 
environment variables at the workspace level. 
●​ Durable Object Storage: Media assets are stored in Cloudflare R2 or Replit Object Storage via the 
S3-compatible API. No local disk dependency. 
●​ Real-Time via WebSocket: Socket.IO rooms scoped to workspace_id push live status events to 
connected clients without polling. 
●​ Audit-First: Every privileged action writes an immutable audit log entry before the action 
completes.

3.3 Invitation Flow 
The invitation flow is token-based to avoid requiring an existing account before receiving an invite. 
1.​ Owner or Manager issues invite: POST /api/v1/workspaces/:wid/invites with { 
email, role }. API validates the inviter has permission to grant the target role. 
2.​ API generates signed JWT invite token: Payload: { workspaceId, inviteeEmail, role, 
invitedByUserId, exp: now + 86400 }. Signed with JWT_SECRET. Token is stored 
(hashed) in an invites table with a used_at column to prevent replay. 
3.​ Email delivery: API enqueues a notification job that sends an email via Resend containing: 
https://app.create.io/accept-invite?token=<JWT>. 
4.​ Recipient clicks link: Frontend sends POST /api/v1/auth/accept-invite with the token. 
API verifies JWT signature, checks expiry, checks invites.used_at IS NULL. 
5.​ Account creation or linking: If a user with inviteeEmail exists, the flow links the existing 
account. If not, the recipient is prompted to set a password; a new users record is created. 

===== PAGE 11 =====
6.​ WorkspaceMember record created: A workspace_members row is inserted with the specified 
role and joined_at = NOW(). The invites.used_at is stamped. A member:joined 
WebSocket event is emitted to the workspace room. 
 
4. Authentication & Authorization 
4.1 Auth Stack Recommendation 
●​ Passport.js with passport-local strategy for email/password, and 
passport-google-oauth20 for Google SSO. 
●​ Access tokens: JWT, 15-minute expiry, signed with JWT_SECRET (HS256). Sent in 
Authorization: Bearer <token> header. 
●​ Refresh tokens: Opaque random string (32 bytes, hex), 7-day expiry. Stored as bcrypt hash in 
refresh_tokens table. Delivered as HttpOnly; Secure; SameSite=Strict cookie named 
__rt. 
●​ Refresh token rotation: Every POST /auth/refresh call invalidates the used token and issues 
a new one. If a revoked token is replayed, all tokens for that user are invalidated (token reuse 
detection). 
●​ PKCE: Required for any public OAuth client (mobile, SPA without backend-for-frontend). Use 
code_challenge_method=S256.

Encryption Key Management: Set SOCIAL_TOKEN_ENCRYPTION_KEY as a 32-byte base64-encoded 
secret in Replit Secrets. The application loads this at startup, validates its length, and derives an 
AES-256-GCM cipher. To rotate keys: increment key_version, add the new key as 
SOCIAL_TOKEN_ENCRYPTION_KEY_V2, run a background job that re-encrypts all rows from version 1 to 
version 2, then remove the old key. The key_version column tells the decryption routine which key 
version to use. 
// typescriptimport { createCipheriv, createDecipheriv, randomBytes } from 
'crypto';const ALGORITHM = 'aes-256-gcm';const KEY = 
Buffer.from(process.env.SOCIAL_TOKEN_ENCRYPTION_KEY!, 'base64');export function 
encryptToken(plaintext: string): string {  const iv = randomBytes(12);  const 
cipher = createCipheriv(ALGORITHM, KEY, iv);  const encrypted = 
Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);  const tag = 
cipher.getAuthTag();  // Format: iv(12b):tag(16b):ciphertext — all base64  
return Buffer.concat([iv, tag, encrypted]).toString('base64');}export function 
decryptToken(encoded: string): string {  const buf = Buffer.from(encoded, 
'base64');  const iv = buf.slice(0, 12);  const tag = buf.slice(12, 28);  const 
ciphertext = buf.slice(28);  const decipher = createDecipheriv(ALGORITHM, KEY, 
iv);  decipher.setAuthTag(tag);  return 
Buffer.concat([decipher.update(ciphertext), 
decipher.final()]).toString('utf8');} 
 
5. Database Schema Extensions 
5.1 Migration Strategy 
●​ Tool: Prisma Migrate for schema-driven migrations; raw SQL escape hatches via 
prisma.$executeRaw for RLS policy DDL (Prisma does not manage RLS natively). 
●​ Additive-only rule: No migration may DROP a column or TABLE in a single step that hasn't been 
deprecated in the previous release. Breaking changes follow: dual-write (new + old column both 
written) → backfill job → read from new column → drop old in subsequent release. 

===== PAGE 14 =====
●​ File naming: YYYYMMDDHHMMSS_description.sql (e.g., 
20260829120000_add_workspace_members.sql). 
●​ Transaction guarantee: Each migration file is wrapped in a transaction. Failure rolls back the 
entire migration, never leaving schema in a partial state. 
●​ Down migrations: Every migration has a corresponding rollback script in 
packages/db/migrations/down/.

5.3 Row-Level Security (RLS) 
RLS is the last line of defence ensuring no API bug can leak cross-workspace data. All application queries 
run as a low-privilege DB role (app_user) which has no bypass privilege. The API sets a session-local 
variable before every query batch. 
-- sql-- Create low-privilege application roleCREATE ROLE app_user LOGIN 
PASSWORD '<generated-strong-password>';GRANT CONNECT ON DATABASE create_db TO 
app_user;GRANT USAGE ON SCHEMA public TO app_user;GRANT SELECT, INSERT, UPDATE, 
DELETE ON ALL TABLES IN SCHEMA public TO app_user;GRANT USAGE, SELECT ON ALL 
SEQUENCES IN SCHEMA public TO app_user;-- Enable RLS on workspace-scoped 
tablesALTER TABLE content_posts ENABLE ROW LEVEL SECURITY;ALTER TABLE 
media_assets ENABLE ROW LEVEL SECURITY;ALTER TABLE publish_jobs ENABLE ROW 
LEVEL SECURITY;ALTER TABLE campaigns ENABLE ROW LEVEL SECURITY;ALTER TABLE 
audit_logs ENABLE ROW LEVEL SECURITY;ALTER TABLE social_connections ENABLE ROW 
LEVEL SECURITY;ALTER TABLE workspace_members ENABLE ROW LEVEL SECURITY;ALTER 
TABLE notifications ENABLE ROW LEVEL SECURITY;-- ── RLS Policies: content_posts 
──CREATE POLICY content_posts_workspace_isolation ON content_posts  AS 
PERMISSIVE FOR ALL TO app_user  USING (workspace_id = 
current_setting('app.current_workspace_id', true)::UUID)  WITH CHECK 
(workspace_id = current_setting('app.current_workspace_id', true)::UUID);-- ── 
RLS Policies: media_assets ──CREATE POLICY media_assets_workspace_isolation ON 
media_assets  AS PERMISSIVE FOR ALL TO app_user  USING (workspace_id = 
current_setting('app.current_workspace_id', true)::UUID)  WITH CHECK 
(workspace_id = current_setting('app.current_workspace_id', true)::UUID);-- 
Apply equivalent policies to all other workspace-scoped tables-- (publish_jobs, 
campaigns, audit_logs, social_connections,--  workspace_members, notifications) 
— follow the same pattern above. 
How the API sets the RLS context: In the resolveWorkspace middleware (Section 4.2), after 
confirming workspace membership, the middleware executes: 
-- sqlSET LOCAL app.current_workspace_id = '<uuid>'; 
SET LOCAL scopes the variable to the current transaction. Because Prisma uses connection pooling, 
always set this within an explicit transaction block or use PgBouncer in transaction mode. Never use SET 
(session-scoped) as it persists across pooled connections.

7.3 Publisher Interface

7.6 Time Zone Handling 
●​ Database: All timestamps stored as TIMESTAMPTZ in UTC. PostgreSQL normalizes on insert. 
●​ Workspace default timezone: Stored as an IANA tz string (e.g., "America/New_York") in 
workspaces.default_timezone. Used as a fallback when the client does not send an offset. 
●​ API input: Frontend sends scheduled_at as ISO 8601 with UTC offset (e.g., 
"2026-09-15T14:00:00-04:00"). The API validates with Zod's z.string().datetime({ 
offset: true }) and stores the UTC-normalized value. 
●​ Scheduler: The cron worker operates entirely in UTC. It never converts timezones internally. 
●​ API output: All timestamps returned as UTC ISO 8601. The frontend converts to the workspace 
timezone for display using the Intl.DateTimeFormat API with the workspace's 
default_timezone. 
●​ DST safety: Because all storage and scheduling is UTC, Daylight Saving Time transitions are 
transparent to the scheduling engine.

9.2 Delivery Channels 
In-app notifications: Written to the notifications table and pushed via Socket.IO 
notification:new event to the target user's session if connected. Users poll GET /notifications 
on reconnect to catch missed notifications. 
Email: The notification BullMQ worker handles email delivery. Use Resend as the primary delivery 
provider with Nodemailer+SendGrid as fallback. Email templates are authored with React Email and 
compiled to static HTML at build time. Never build email HTML at runtime via string concatenation. 
// typescript// notificationWorker.ts — email deliveryimport { Resend } from 
'resend';import { PublishFailedEmail } from '@create/emails';const resend = new 
Resend(process.env.RESEND_API_KEY);async function 
sendPublishFailedEmail(payload: PublishFailedPayload) {  await 
resend.emails.send({    from: 'CREATE <notifications@create.io>',    to: 
payload.recipientEmail,    subject: `Post publish failed: 
${payload.postTitle}`,    react: PublishFailedEmail({ ...payload }),  });} 
Outbound webhooks: If a workspace has configured a webhook_url (stored in workspaces), every 
notification event is also POSTed to that URL as a JSON payload. The request includes a 
X-Create-Signature header containing the HMAC-SHA256 signature of the raw body using the 
workspace's webhook_secret. Consumers must verify this signature before processing.

11. Security Hardening Checklist 
Each item must be verified before any public production deployment. Assign an owner for each item 
during sprint planning. 
●​ Helmet.js HTTP headers: Install and configure helmet() as the first middleware. Enables CSP, 
HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy. Customize CSP to allow only 
known CDN origins. 

===== PAGE 43 =====
●​ CORS restricted to whitelist: Set origin to the array from FRONTEND_URL + CORS_ORIGINS. 
Never use origin: '*'. Credentials mode requires explicit origin, not wildcard. 
●​ SQL injection: parameterized queries only: Prisma parameterizes by default. Any raw SQL (e.g., 
RLS context setting) must use tagged template literals (prisma.$queryRaw\`...\`), never 
string interpolation. Lint rule: ban $executeRawUnsafe except for SET LOCAL statements with 
UUID-validated inputs. 
●​ XSS: sanitize user-supplied HTML: All rich text stored in body_json must be sanitized before 
storage using DOMPurify (server-side via dompurify + jsdom). Never render stored HTML 
without re-sanitizing in the frontend. 
●​ CSRF: double-submit cookie: For all state-changing form endpoints, use the double-submit 
cookie pattern. Refresh token cookie is SameSite=Strict; HttpOnly; Secure. AJAX 
requests send a CSRF token in header matched against a cookie value. 
●​ HMAC webhook verification with replay protection: All inbound webhooks at 
/webhooks/:platform must verify HMAC-SHA256 signature. Reject requests where the 
embedded timestamp is older than WEBHOOK_TOLERANCE_SECONDS (default: 300 seconds) to 
prevent replay attacks. 
●​ File upload: magic byte MIME validation: Validate MIME type by reading the first 8 bytes (magic 
numbers) using the file-type npm package. Do not trust the Content-Type header or file 
extension alone. Enforce per-type size limits before processing. 
●​ File upload: virus scan stub: Add a ClamAV scan step in the media-process worker before 
marking assets as ready. For MVP, implement the interface with a no-op and document the stub 
— full ClamAV integration is a required pre-launch item. 
●​ OAuth state parameter validation: Generate a cryptographically random state value (32 bytes, 
hex) for every OAuth2 authorization code flow. Store state in a short-lived (10 min) Redis key. 
Reject callbacks where state does not match. This prevents CSRF on the OAuth flow. 
●​ Refresh token rotation on use: Every successful POST /auth/refresh must revoke the 
submitted token and issue a new one. If a revoked token is detected being replayed, set 
revoked_at on all tokens for that user (token reuse detection = account breach signal). 

===== PAGE 44 =====
●​ Audit log all privileged actions: Write an audit_logs record before (not after) any state change 
involving: member role changes, member removal, social connection add/remove, post 
approval, publish-now, workspace setting changes, and export actions. Use a DB transaction to 
make the audit write atomic with the action. 
●​ Rate limiting on auth endpoints: Apply authLimiter (5 req/min per IP) specifically to POST 
/auth/login, POST /auth/register, and POST /auth/accept-invite. Standard 
authenticatedLimiter (200 req/min) applies to all other authenticated routes. 
●​ RLS enforced at DB layer: Confirm RLS is active by running SELECT relrowsecurity FROM 
pg_class WHERE relname = 'content_posts' → must return true. Write an integration 
test that asserts a query with workspace A's context cannot return workspace B's rows. 
●​ Encrypt social OAuth tokens at rest: All access_token and refresh_token values in 
social_connections must be encrypted with AES-256-GCM before INSERT/UPDATE and 
decrypted after SELECT. Never log decrypted token values. 
●​ Dependency scanning: npm audit in CI: Add npm audit --audit-level=moderate as a 
required CI step. Any moderate or higher severity vulnerability fails the build until resolved or 
explicitly suppressed with justification. 
●​ Secrets never logged: Configure the Winston logger to redact any log entries containing fields 
named password, token, access_token, refresh_token, secret, or authorization. Use 
a custom formatter or the winston-sanitize plugin. 
●​ HTTPS only: Replit Cloud Run enforces TLS termination. Ensure the Express app sets 
app.set('trust proxy', 1) to correctly read forwarded IP addresses. Never serve mixed 
content. 
●​ Email verification before publishing: Require users.email_verified_at IS NOT NULL 
before a user can publish content or connect social integrations. Send verification email on 
registration; resend via POST /auth/resend-verification.

12.5 Rollback Strategy 
●​ Database migrations: Every migration has a corresponding down migration in 
packages/db/migrations/down/. Rollback command: prisma migrate resolve 
--rolled-back <migration_name> followed by manual execution of the down SQL file. 
●​ Feature flags: A feature_flags table (key TEXT PRIMARY KEY, enabled BOOLEAN, 
workspace_id UUID nullable) allows disabling the new publishing engine without a 
redeploy. Workers check the flag before processing. The API falls back to the legacy export flow if 
the flag is off. 
●​ Blue/green deployment: If Replit deployment budget allows, maintain two deployment slots: 
production (current stable) and staging (next release). Traffic can be switched back to the 
previous slot within seconds via the Replit dashboard if a critical bug is detected post-deploy. 
●​ Data backups: Configure daily automated PostgreSQL backups. Before each phase migration, 
trigger a manual backup and verify restore-ability in a separate environment.

Appendix A: Glossary 
 
Term 
Definition 
Workspace 
The primary tenant unit in CREATE. Represents one team or brand 
account. All content, media, social connections, and members belong to 
exactly one workspace. The billing unit for SaaS subscriptions. 
Member Role 
An authorization level assigned to a user within a specific workspace. 
Roles are: Viewer, Creator, Editor, Manager, Owner. A user may hold 
different roles in different workspaces simultaneously. 
Publish Job 
A record in the publish_jobs table representing a single attempt to 
publish a content_post to a specific social platform. One content post 
targeting three platforms produces three independent publish jobs. 
Content Post 
A record in the content_posts table representing a piece of social 
media content in any lifecycle state (draft through published). Contains 
rich text body, media references, scheduling metadata, and platform 
targets. 

===== PAGE 51 =====
Term 
Definition 
OAuth Token Vault 
The social_connections table, which stores per-workspace, 
per-platform OAuth access and refresh tokens encrypted with 
AES-256-GCM. The "vault" abstraction isolates token storage and 
decryption from the rest of the application. 
Dead Letter Queue 
The state of a BullMQ job that has exhausted all retry attempts. In 
CREATE, a dead-lettered publish job has status = 'failed' and 
retry_count = 4. It remains in the database for audit purposes and 
can be manually retried via the API. 
RLS (Row-Level Security) 
A PostgreSQL feature that restricts which rows a database role can 
SELECT, INSERT, UPDATE, or DELETE. In CREATE, RLS policies on 
workspace-scoped tables enforce tenant isolation at the database layer, 
independent of API logic. 
BullMQ 
A Node.js job queue library backed by Redis. Used in CREATE for the 
content-publish, media-process, and notification queues. 
Provides durable job storage, retry logic, delayed jobs, and concurrency 
control. 
Presigned URL 
A time-limited, pre-authorized URL generated by the API server that 
allows a client to upload a file directly to object storage (R2 or Replit 
Object Storage) without routing the file bytes through the API server. 
Generated using the AWS SDK getSignedUrl function. 
PKCE (Proof Key for Code 
Exchange) 
An OAuth2 extension (RFC 7636) that prevents authorization code 
interception attacks. Required for public OAuth clients (SPAs, mobile 
apps). The client generates a random code_verifier, sends its 
SHA-256 hash (code_challenge) in the authorization request, and 
proves possession of the verifier when exchanging the code for tokens.
