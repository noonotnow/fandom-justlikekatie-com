Yes. That’s the exact seam.

Right now it sounds like **export is doing double duty**:

1. **Produce/share the artifact**
2. **Persist the grid as a saved object**

That works as a bootstrap behavior, but it creates product confusion because exporting is an *output action*, while saving is a *collection/state action*.

They should become separate verbs.

## Clean model

A grid should have its own lifecycle:

### 1. Proposed grid

System-generated or manually assembled, but not yet saved.

State: temporary / draft / session-local.

User actions:

- swap cards
- regenerate
- change lens
- export
- save grid
- send to CREATE

### 2. Saved grid

A durable collection object.

State: saved to user’s collection.

User actions:

- reopen
- rename
- tag/lens
- edit/remix
- export
- duplicate
- send to CREATE
- delete

### 3. Exported grid

A rendered artifact event/file.

State: output/log, not the source of truth.

User actions:

- download
- share
- copy
- maybe view export history

## The product correction

Instead of:

> Export grid → grid becomes saved
> 

It should be:

> Save grid → grid becomes part of collection
> 

> Export grid → PNG/share artifact is produced and logged
> 

They can happen together if the user wants, but they should not be the same action.

## Best UX pattern

I’d make three buttons or actions, probably with one primary action depending on context:

### **Save grid**

Meaning:

> “Keep this composition in my collection.”
> 

Stores:

- grid ID
- 9 card references
- order/slot positions
- lens/source
- star
- vibe/spell
- rationale
- created date
- edited date
- maybe title

### **Export / Share**

Meaning:

> “Render this as an image or shareable artifact.”
> 

Stores/logs:

- export event
- export variant
- timestamp
- image IDs
- edition tier
- whether this grid was saved first
- destination/share method if known

But does **not** imply saving unless explicitly chosen.

### **Send to CREATE**

Meaning:

> “Turn this into a post/publishing workflow.”
> 

Creates:

- Idea Packet / CREATE object
- enriched handoff context
- caption/copy workflow
- scheduling/publishing state

## Helpful microcopy

To avoid ambiguity:

- **Save grid** — “Keep this 3×3 in your collection”
- **Export card** — “Download or share this image”
- **Send to CREATE** — “Make a post from this grid”

If the user exports an unsaved grid, you can offer:

> “Export complete. Save this grid to your collection?”
> 

Or a toggle:

> `[x] Save grid to collection after export`
> 

But the default should probably be explicit rather than magical.

## Why this matters

Separating these verbs gives you better data and better UX:

### Better data

You can distinguish:

- grids Katie liked enough to save
- grids Katie exported
- grids Katie sent to CREATE
- grids Katie abandoned
- grids Katie edited heavily before saving/exporting

Those are different signals.

### Better recommendations

A saved-but-not-exported grid means:

> promising / maybe later
> 

An exported grid means:

> output-worthy
> 

A sent-to-CREATE grid means:

> content pipeline-worthy
> 

A heavily edited grid means:

> proposal was close but needed taste correction
> 

That becomes very useful for future pre-curation.

### Better product boundary

Saving belongs to **Collections**.  

Exporting belongs to **Sharing**.  

Scheduling/publishing belongs to **CREATE**.

Clean.
